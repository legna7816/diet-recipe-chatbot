# Diet Recipe Chatbot

식약처 공공 레시피 데이터(1,156건)를 기반으로 한 RAG 기반 다이어트 레시피 추천 챗봇.
[rag_api](https://github.com/legna7816/rag_api)에서 학습한 RAG 기술(FAISS + LLM)을 실제 서비스 형태로 발전시킨 프로젝트.

## 사용 기술
- Python, FastAPI, Docker, GitHub Actions
- MySQL (PyMySQL) — 세션 및 대화 히스토리 저장
- 임베딩: `jhgan/ko-sroberta-multitask`
- 생성 모델: `Qwen/Qwen2.5-1.5B-Instruct` (CPU 추론)
- 벡터 검색: FAISS (`IndexFlatIP`)
- 데이터: 식약처 조리식품 레시피 DB Open API (`COOKRCP01`)

## 구조
```
HTTP 요청(질문 + session_id)
  → MySQL에서 최근 대화 3턴 + 직전 레시피 조회
  → FAISS 검색 (현재 질문 기준)
  → 직전 레시피와 이번 검색 결과 병합 (대화 맥락 유지)
  → 히스토리 + 레시피 목록으로 LLM 답변 생성
  → 이번 턴을 MySQL에 트랜잭션으로 저장
```

## 실행 방법

1. 패키지 설치
```
python -m pip install -r requirements.txt
```
2. MySQL에서 스키마 생성
```sql
source schema.sql
```
3. 프로젝트 루트에 `.env` 작성 (레포에는 포함되지 않음)
```
DB_HOST=localhost
DB_PORT=3306
DB_USER=root
DB_PASSWORD=비밀번호
DB_NAME=diet_recipe_chatbot
```
4. 레시피 인덱스 생성 (최초 1회)
```
python build_recipe_documents.py
python build_recipe_index.py
```
5. 서버 실행 → `http://127.0.0.1:8000/docs`
```
uvicorn main:app --reload
```

## API
| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/chat` | 대화 (session_id 없으면 새로 발급) |
| GET | `/sessions/{id}/history` | 세션 전체 대화 기록 조회 |
| DELETE | `/sessions/{id}` | 세션 삭제 (대화 기록 함께 삭제) |
| POST | `/search` | 레시피 검색만 수행 (생성 없음) |
| GET / POST | `/recipes` | 레시피 목록 조회 / 추가 |

## 진행 과정

### 1. RAG API를 챗봇 서비스로 전환
- `rag_api`의 코드를 베이스로, 엔드포인트(`/ask`→`/chat`, `/documents`→`/recipes`)와 명칭을 챗봇 목적에 맞게 재정비

### 2. 실제 공공데이터 파이프라인 구축
- 식약처 Open API에서 전체 레시피(1,156건) 수집 → 자연어 문서로 변환 → FAISS 인덱싱
- **데이터 무결성 검증 추가**: 초기 버전은 배치 요청 중 일부가 누락돼도 감지하지 못해, 1,156건 중 95건이 조용히 빠지는 문제가 있었음. 배치별 수신 개수를 요청 개수와 대조하고, 부족하면 재시도, 최종 검증 실패 시 파일을 저장하지 않도록 수정

### 3. 대화 히스토리 & 세션 관리 — v1 → v2 → v3

챗봇과 단순 검색 API의 핵심 차이는 "이전 대화를 기억하는가"에 있음. 세 단계에 걸쳐 발전시킴.

**v1 — 메모리(dict) 저장 + 질문 결합 검색 (실패)**
- `session_id`로 사용자별 대화를 구분하고 Python dict에 저장
- 후속 질문의 맥락을 위해 이전 사용자 질문들을 현재 질문에 이어붙여 검색
- 결과: "그거 칼로리는 얼마야?"의 "칼로리"라는 단어가 임베딩을 왜곡시켜, 직전 주제(매운 음식)와 무관한 샐러드류가 검색됨

**v2 — 메모리 저장 + 직전 레시피 병합 (성공, 단 휘발성)**
- 검색은 현재 질문으로만 수행하고, 직전 턴에서 사용한 레시피를 세션에 보관했다가 이번 검색 결과와 병합해 프롬프트에 포함
- **병합 순서 문제 발견**: 새 검색 결과를 앞에 두자 모델이 "그거"를 새로 검색된 레시피로 오해함. 이전 레시피를 앞에 배치하고, 시스템 프롬프트에 "목록 앞쪽일수록 이전 대화의 요리"라고 명시하자 해결
- 한계: 서버를 재시작하면 모든 대화가 사라짐

**v3 — MySQL 영속화 (현재)**
- 세션과 메시지를 1:N 관계의 두 테이블로 정규화

```
chat_sessions (session_id PK, last_recipes, created_at, updated_at)
      1
      │
      N
chat_messages (id PK, session_id FK → ON DELETE CASCADE, role, content, created_at)
```

- 검증: 대화 후 서버를 재시작한 상태에서 후속 질문("그거 칼로리 얼마야?")을 보냈을 때, 재시작 이전에 추천한 요리(매운닭날개구이, 285kcal)를 정확히 참조함

### 4. v3 설계 포인트
- **트랜잭션**: 한 턴의 저장(질문 INSERT + 답변 INSERT + 직전 레시피 UPDATE)을 하나의 트랜잭션으로 묶음. `autocommit=False`로 두고 성공 시 `commit()`, 예외 시 `rollback()` → "질문만 저장되고 답변은 없는" 반쪽 상태 방지
- **파라미터 바인딩**: 모든 쿼리를 `%s` 플레이스홀더로 작성해 드라이버가 값을 바인딩(JDBC `PreparedStatement`의 `?`와 동일) → SQL 인젝션 방지
- **대화 길이 제한 위치 변경**: v2는 메모리 절약을 위해 저장 시점에 오래된 대화를 삭제했지만, v3는 전체 기록을 DB에 보존하고 프롬프트에 넣을 때만 최근 3턴을 조회 → 기록은 남기면서 프롬프트 길이는 제한
- **Fail fast**: 서버 시작 시 DB 연결과 테이블 존재를 확인해, 설정 오류를 첫 사용자 요청이 아니라 기동 시점에 바로 드러냄
- **설정 분리**: DB 접속 정보를 `.env`로 분리하고 `.gitignore`에 포함해 비밀번호가 레포에 올라가지 않도록 함

### 5. 프롬프트 안정화
레시피 데이터가 실제 서비스처럼 길어지자 다음 문제들이 반복적으로 발생했고, 각각에 대응:
- **목록 밖 요리 나열**: 실제 목록에 없는 요리를 지어내며 답변을 늘어놓음 → 시스템 프롬프트를 번호 매긴 짧고 단정적인 규칙으로 재작성, "최대 2개까지만 언급" 등 구체적 제약 추가
- **언어 혼입**: 한국어 답변 중간에 중국어 단어가 섞임 → "한국어로만 답합니다" 규칙 명시
- **응답 불안정**: `temperature=0.7`에서 같은 질문에도 품질이 크게 흔들림 → `0.3`으로 낮춤
- `max_new_tokens`를 250→180으로 줄여 장황한 나열 자체를 구조적으로 제한

## 트러블슈팅 기록
- **MySQL 외래키 생성 실패 (ERROR 1824)**: 부모 테이블 생성 시 테이블명 오타(`chat_session`)로 자식 테이블이 참조할 `chat_sessions`가 존재하지 않아 발생. `SHOW CREATE TABLE`로 실제 참조 대상을 확인한 뒤 잘못 생성된 테이블을 정리
- **PowerShell에서 SQL 파일 실행 실패**: PowerShell은 `<` 리다이렉션을 지원하지 않아 `mysql -u root -p < schema.sql` 불가 → MySQL 프롬프트에서 `source` 명령으로 실행
- **가상환경 패키지 불일치**: `pip`과 `python`이 서로 다른 환경을 가리켜 설치한 패키지를 import하지 못함 → `python -m pip`으로 설치 대상을 명시

## 핵심 인사이트
1. **RAG 검색어와 대화 맥락은 별도로 다뤄야 한다.** 대화 히스토리를 그대로 검색어에 이어붙이면 오히려 검색 품질이 나빠질 수 있다. 검색은 현재 질문에 집중시키고, 맥락 유지는 별도 메커니즘(이전 결과 병합)으로 처리하는 것이 안정적이다.
2. **프롬프트 내 정보 순서가 모델의 해석에 영향을 준다.** 같은 정보라도 배치 순서에 따라 모델이 "무엇이 최근 맥락인지" 다르게 판단할 수 있다.
3. **데이터 파이프라인은 성공 여부를 명시적으로 검증해야 한다.** 배치 처리 중 일부 실패가 조용히 넘어가면, 실제로는 손상된 결과물이 정상처럼 보일 수 있다.
4. **저장과 조회의 정책은 분리할 수 있다.** 기록은 전부 보존하되 모델에 넘기는 양만 제한하면, 감사/분석용 데이터와 추론 성능을 동시에 챙길 수 있다.
5. **작은 로컬 모델의 안정성은 여러 변수의 조합으로 확보해야 한다.** 프롬프트 구조, temperature, 출력 길이 제한을 함께 조정해야 실사용 가능한 일관성이 나온다.

## 한계 및 다음 단계
- **Docker 실행 시 DB 접속 불가**: 컨테이너 내부의 `localhost`는 호스트 PC가 아니므로 로컬 MySQL에 접속할 수 없음 → docker-compose로 MySQL 컨테이너를 함께 구성할 예정
- **CI에서 DB 로직 미검증**: 현재 CI는 문법 검사와 Docker 빌드만 수행 → 테스트용 MySQL 서비스 컨테이너를 붙인 통합 테스트 추가 검토
- 대화 주제가 완전히 바뀌는 경우(예: 매운 음식 → 샐러드) 이전 레시피가 불필요하게 계속 포함될 수 있음
- 요청마다 DB 연결을 새로 생성 → 트래픽 증가 시 커넥션 풀 도입 필요
- 즐겨찾기, 사용자별 선호도 저장 등 서비스 기능은 아직 미구현
