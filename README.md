# Diet Recipe Chatbot

식약처 공공 레시피 데이터(1,156건)를 기반으로 한 RAG 기반 다이어트 레시피 추천 챗봇.
[rag_api](https://github.com/legna7816/rag_api)에서 학습한 RAG 기술(FAISS + LLM)을 실제 서비스 형태로 발전시킨 프로젝트.

## 사용 기술
- Python, FastAPI, Docker, GitHub Actions
- 임베딩: `jhgan/ko-sroberta-multitask`
- 생성 모델: `Qwen/Qwen2.5-1.5B-Instruct` (CPU 추론)
- 벡터 검색: FAISS (`IndexFlatIP`)
- 데이터: 식약처 조리식품 레시피 DB Open API (`COOKRCP01`)

## 구조
```
HTTP 요청(질문 + session_id)
  → FAISS 검색 (현재 질문 기준)
  → 직전 턴 레시피와 병합 (대화 맥락 유지)
  → 히스토리 + 레시피 목록으로 LLM 답변 생성
  → 세션에 대화 기록 저장
```

## 진행 과정

### 1. RAG API를 챗봇 서비스로 전환
- `rag_api`의 코드를 베이스로, 엔드포인트(`/ask`→`/chat`, `/documents`→`/recipes`)와 명칭을 챗봇 목적에 맞게 재정비

### 2. 실제 공공데이터 파이프라인 구축
- 식약처 Open API에서 전체 레시피(1,156건) 수집 → 자연어 문서로 변환 → FAISS 인덱싱
- **데이터 무결성 검증 추가**: 초기 버전은 배치 요청 중 일부가 누락돼도 감지하지 못해, 1,156건 중 95건이 조용히 빠지는 문제가 있었음. 배치별 수신 개수를 요청 개수와 대조하고, 부족하면 재시도, 최종 검증 실패 시 파일을 저장하지 않도록 수정 → 데이터 파이프라인은 실패를 조용히 삼키면 안 된다는 것을 직접 확인

### 3. 세션 기반 대화 히스토리 구현
챗봇과 단순 검색 API의 핵심 차이는 "이전 대화를 기억하는가"에 있음. `session_id`로 사용자별 대화를 구분하고, 최근 N턴만 유지하도록 구현(v1: 메모리 저장, 향후 MySQL로 교체 예정).

**검색 맥락 유지 방식 시행착오:**
- 1차 시도: 이전 사용자 질문들을 현재 질문에 이어붙여 검색 → 실패. "그거 칼로리는 얼마야?"에 "칼로리"라는 단어가 임베딩을 왜곡시켜, 직전 대화 주제(매운 음식)와 무관한 레시피가 검색됨
- 2차 시도(채택): 검색은 현재 질문으로만 수행하고, 직전 턴에서 언급한 레시피를 별도로 세션에 보관했다가 이번 검색 결과와 병합해 프롬프트에 포함 → 성공

**병합 순서의 영향:**
새로 검색된 레시피를 앞에, 이전 레시피를 뒤에 배치했을 때 모델이 "그거"를 최근 언급이 아닌 새로 검색된 레시피로 잘못 해석하는 문제가 발생. 이전 레시피를 앞쪽에 배치하도록 순서를 바꾼 뒤 해결됨 — 프롬프트 내 정보의 순서가 모델의 참조 해석에 실질적 영향을 준다는 것을 확인.

### 4. 프롬프트 안정화
레시피 데이터가 실제 서비스처럼 길어지자 다음 문제들이 반복적으로 발생했고, 각각에 대응:
- **목록 밖 요리 나열**: 모델이 실제 목록에 없는 요리를 계속 지어내며 답변을 늘어놓는 경향 → 시스템 프롬프트를 번호 매긴 짧고 단정적인 규칙으로 재작성, "최대 2개까지만 언급" 등 구체적 제약 추가
- **언어 혼입**: 한국어 답변 중간에 중국어 단어가 섞이는 현상 발생 → "한국어로만 답합니다" 규칙 명시로 해결
- **응답 불안정**: `temperature=0.7`에서 같은 질문에도 답변 품질이 크게 흔들림 → `0.3`으로 낮춰 지시 준수도를 높임
- `max_new_tokens`를 250→180으로 줄여 장황한 나열 자체를 구조적으로 제한

## 핵심 인사이트

1. **RAG 검색어와 대화 맥락은 별도로 다뤄야 한다.** 대화 히스토리를 그대로 검색어에 이어붙이면 오히려 검색 품질이 나빠질 수 있다. 검색은 현재 질문에 집중시키고, 맥락 유지는 별도 메커니즘(이전 결과 병합)으로 처리하는 것이 안정적이다.
2. **프롬프트 내 정보 순서가 모델의 해석에 영향을 준다.** 같은 정보라도 배치 순서에 따라 모델이 "무엇이 최근 맥락인지" 다르게 판단할 수 있다.
3. **데이터 파이프라인은 성공 여부를 명시적으로 검증해야 한다.** 배치 처리 중 일부 실패가 조용히 넘어가면, 실제로는 손상된 결과물이 정상처럼 보일 수 있다.
4. **작은 로컬 모델의 안정성은 여러 변수의 조합으로 확보해야 한다.** 프롬프트 구조, temperature, 출력 길이 제한을 함께 조정해야 실사용 가능한 수준의 일관성이 나온다.

## 한계 및 다음 단계
- 세션이 메모리에만 저장되어 서버 재시작 시 모든 대화가 소실됨 → **다음 단계: MySQL로 세션/히스토리 저장소 교체**
- 대화 주제가 완전히 바뀌는 경우(예: 매운 음식 → 샐러드) 이전 레시피가 불필요하게 계속 포함될 수 있음 (query rewriting으로 개선 가능하나 CPU 환경에서는 추가 LLM 호출 비용이 큼)
- 즐겨찾기, 사용자별 선호도 저장 등 서비스 기능은 아직 미구현
